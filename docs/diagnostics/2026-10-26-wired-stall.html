为什么重点查网卡查询

Windows 单线程 Tokio 事件循环
    ├─ 输入、DTLS、KCP、心跳、IPC
    ├─ 每 30 秒：发现服务 / 网络标识刷新
    └─ 每 30 秒：监听地址核对
                  ↓ 同步调用 netdev
             枚举网卡 → 查询网关 MAC → SendARP
                  ↓ 若阻塞
           同一事件循环的其他任务不能推进

  • mousehop/src/service.rs:1217：同步 discovery refresh，随后刷新网络标识；后者调用 current_network_id()。
  • mousehop/src/listen.rs:650：30 秒定时分支直接枚举监听地址。
  • 依赖 netdev 0.43.0 的 Windows 枚举实现查询网关时调用同步 SendARP。

网线与 Wi-Fi 的区别

实际 Mac → Windows 路由使用 USB Ethernet en6。短时 20 包 ICMP 测试无丢包，平均 0.914 ms，接口计数未见错误／丢弃。它只能说明短采样链路正常，不能排除故障时刻的链路问题。

有线场景可能改变网卡集合、路由／网关和邻居解析路径，使同步查询变慢；当前 Windows 还有虚拟网卡与 Mihomo 接口。尚未在受控条件下切换 Wi-Fi 做相同输入和调度对照，所以不能断言是 USB 网卡、代理或网线损坏。

窗口关闭问题的边界

Mac 的预期行为是点击 × 隐藏窗口、保留菜单栏与服务，不是退出进程。mousehop-gtk/src/lib.rs:510 已安装 hide-on-close 回调。

17:16:19 的 GUI 栈显示主线程在 GTK/AppKit 事件等待中，没有抓到关闭失败。下一次失败时需同时采集 GUI 栈、窗口／模态状态和关闭回调是否执行；检查是否未收到 close-request、被模态窗口阻挡，或隐藏后又被重新呈现。以上均为待验证方向。

建议修复与验收

  1. 先隔离慢网络查询。 后台有界执行、合并重复快照；仅将结果送回服务事件循环，避免在服务分支中等待慢查询而暂停输入分发。失败快照不能直接当作“网卡已消失”。
  2. 不放宽输入安全超时。 也不关闭输入恢复、不更换 GUI 框架来绕过卡顿。
  3. 独立复现 × 故障。 用触控板验证“隐藏 → 菜单栏重开”，并在失败瞬间抓栈后再决定修复。
  4. 性能纳入验收。 注入数秒慢查询仍应持续服务输入／心跳；查询最多一项在途、无无限任务堆积。实机有线与 Wi-Fi 各覆盖多个 30 秒刷新周期，检查事件循环延迟、CPU、线程数及停顿。
